## 三、本次新暴露的问题（按优先级）

### 3.1 [P1·新] `delete` 前缀 → `file_delete` 误报（与 get/post 同构）

**现象**：Taint 结果中 11 条 `mcp_tool_parameter → file_delete`（`delete_range` / `delete_worksheet` / `delete_sheet_rows` / `delete_sheet_columns` / `delete_cols` / `delete_rows` / `delete_sheet` 各参数），并融合成 1 条 `delete_range_operation(...)` finding。

**根因**：`infer.rs::NAME_PREFIX_CATEGORY` 中的 `("delete", "file_delete")`。这些函数都是 **openpyxl 工作表/单元格/行列的内部修改操作**（`delete_range` 删的是单元格范围，`delete_worksheet` 删的是 sheet），**不是文件删除**。真正删文件的动词早已在 sink catalog 里显式建模：

```
# models/sinks/python.toml:152
category = "file_delete"
patterns = ["os.remove", "os.unlink", "os.rmdir", "shutil.rmtree", "Path.unlink", "Path.rmdir"]
```

裸 `delete` 前缀只产生误报，与上一轮 `get`/`post` 完全同构。

**修复**：从 `NAME_PREFIX_CATEGORY` 删除 `("delete", "file_delete")`（保留 `remove`/`unlink`/`rmdir` —— 这三个是强文件语义）。加回归测试 `delete_prefix_is_not_inferred_as_file_delete`。**注意**：`remove` 也存在同样歧义风险（`remove_range`），本次虽未触发，建议一并观察。

### 3.2 [P1] `file_read` / `file_write` 双向过计数

**现象**：同一个 `filepath` 参数同时流向 `file_read` 与 `file_write`，如
`copy_range:sheet_name → file_read:sheet.py:271`（`load_workbook`）**且** `copy_range:sheet_name → file_write:sheet.py:306`（写回）。

**根因**：layer-2 `package_inference.toml` 对 openpyxl 设 `read_category=file_read` + `write_category=file_write`，按方法名前缀拆分。「修改文件」这类操作天然读+写，于是每个参数 × 每个 sink 组合各报一条，造成 ~19 条同构 `file_read` + 若干 `file_write` 的重复爆炸。

**修复方向**：在 taint 结果层按 `(source_id, sink_category, 逻辑文件)` 去重；或对同一 source 命中「读 + 写」同一点时只保留一条并归一为 `file_modify`（或保留严重度更高者）。

### 3.3 [P2] Fusion 跨文件聚合未兑现（同一 CVE 拆成 4 条）

**现象**：路径穿越 CVE 本体在 Fused Findings 里以 4 条独立 finding 出现：

| Finding | 严重度/置信度 | 来源 |
|---|---|---|
| `mcp/tool-param-to-path-traversal` @ workbook.py:23/66 | Medium / **High** | taint + codeql |
| `..` @ __main__.py:13 | High / Medium | rule |
| `taint: → file_read` @ server.py（get_excel_path → full_path） | Medium / Medium | taint |
| `Arbitrary file access … get_excel_path` | High / Medium | agent |

**根因**：`matcher.rs` 的**两个阶段都要求同文件**——stage1（proximity）`file_key 相等 && 行距 ≤ line_proximity`，stage2（category）`file_key 相等 && category 归一化相等`。而这 4 条分布在不同文件（workbook.py / __main__.py / server.py / agent 无定位），category 也不同（path_traversal / path_traversal / file_read / unknown），因此永远合不到一起。

**修复方向**：这是设计改动，有过度合并风险。可选：
1. 在 matcher 中引入「漏洞签名」维度（如 sink 函数名 `get_excel_path` / `load_workbook`）作为跨文件、跨 category 的聚合键；
2. 或增加 path_traversal 与 file_read 的「类别族」映射，允许族内跨文件合并；
3. 合并后置信度取多线一致（目标：`[High, High]`）。

**需用户确认后再动。**

### 3.4 [P2·观察] `file_delete` finding 的 category/severity 标注异常（需核实）

Fused Findings 第 2 条：标题 `taint: mcp_tool_parameter → file_delete`，但 `— category` 字段显示 **`file_write`**，且 `sev=High`（而 file_delete 底层 sink 为 Medium，且 `normalize_category("file_delete")` 应返回 `file_delete`）。

按 `merger.rs::build_category` 的多数投票逻辑，纯 file_delete taint 组的 category 应为 `file_delete`。出现 `file_write` + `High` 说明该组可能混入了 file_write taint，或 `group_max_severity` 取到了他源。**需代码级核实**是否 category/severity 取错（若属实，融合输出的 category 可信度存疑）。

### 3.5 [P3·低] Agent 线非确定性（4 → 3）

`preview_only 参数声明却未生效 → 全量数据外带`（High）这条在本次运行**消失**，取而代之出现 `Unauthenticated network exposure of destructive file-manipulation tools`（High）。属 LLM 采样方差，非代码 bug，但说明 **B 线（agent）作为差分基准时结果不稳定**，多次运行应取并集/交集，或固定 temperature 提升可复现性。

### 3.6 [观察] 进化 a2=21 仍非零

`Migration: b1=0 a1=0 a2=21 b2=0 b0=0 still_ambiguous=0`，决策 `promote`。a2=21 即 21 条被判为「A 线独有」的 taint 误报——正是 §3.1（file_delete）与 §3.2（file_read/file_write）的残余噪声。上轮已核实 `delta`（待持久化模型 pattern）与 `a2`（taint finding）**类型不同、无直接交集**，故 promote 不会把误报当模型持久化；但 a2 规模本身应随 3.1/3.2 的修复而收敛，可作为修复效果的下游验证信号。

## 四、调整方案（按优先级）

| 优先级 | 问题 | 调整 | 预期效果 | 风险 |
|---|---|---|---|---|
| **P1-A** | `delete` 前缀 → file_delete 误报（§3.1） | 从 `NAME_PREFIX_CATEGORY` 删除 `("delete", …)`；加回归测试 | 消除 11 条 file_delete FP + 1 条误融合 finding | 极低（真删文件动词已在 catalog） |
| **P1-B** | file_read/file_write 双向过计数（§3.2） | taint 层按 `(source, sink_category, 位置)` 去重 / 读+写归一 | 170 → 进一步显著下降，每条可读 | 低（需保证不吞掉真实读写双漏洞） |
| **P2** | Fusion 跨文件聚合（§3.3） | 引入 sink 签名 / 类别族维度跨文件合并 | 同一 CVE 合并为 1 条 `[High, High]` | **中（过度合并风险，需用户确认）** |
| **P2** | category/severity 标注异常（§3.4） | 核实 `build_category` / `group_max_severity` 对该组的取值 | 修复潜在标注 bug | 低 |
| **P3** | Agent 非确定性（§3.5） | 多次 agent 取并集 / 固定 temperature | 差分基准更稳定 | 低（可能增 token 成本） |

## 五、结论

本次复跑确认：**CodeQL 已能正常出结果并命中真实 CVE（用户最关注的问题已解决）**，P0/P1 修复闭环有效。剩余问题集中在两类：

1. **同类启发式误报的"扫尾"**（`delete` → file_delete），修法与 get/post 一致，成本低、可立即做；
2. **聚合/去重能力**（fusion 跨文件、taint 双向去重），属设计层改动，需权衡过度合并风险。

建议顺序：先落 **P1-A**（立即、零风险、消除当前最扎眼的 file_delete 误报），再评估 **P1-B**（去重）与 **P2**（跨文件聚合，需一次设计确认）。
