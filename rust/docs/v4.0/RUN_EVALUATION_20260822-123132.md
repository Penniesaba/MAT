## 一、总体结论（一句话）

> **Agent 线（B 线）是当前唯一可靠产出真实漏洞的线；Taint 线（A 线）噪声极大（212 条、大量误报）；CodeQL 线完全失效（0 条结果，MaD 注入触发致命错误 `sinkModel Expected 4, but was 3` 直接 kill 掉整条分析）。** 三条线严重失衡，差分进化目前是在「一条强线 + 一条噪声线 + 一条瘫痪线」之间做对比，违背了「MaD 必须正常运行、深度参与」的硬要求。

## 三、CodeQL 故障根因（P0，已复现定位）

### 3.1 现象

```
CodeQL analyze failed (exit code 2):
A fatal error occurred: A tuple in a data extension for the extensible
predicate 'sinkModel' has an incorrect number of columns. Expected 4, but was 3.
```

结果：整条 `codeql database analyze` 被 kill，**CodeQL Results = 0**。

### 3.2 根因

`models.rs::write_model_pack_dir` 把 **python 与 javascript 两个语言的 `.model.yml` 写进同一个临时 pack**，且 `qlpack.yml` 用通配符声明：

```yaml
dataExtensions:
  - "*.model.yml"      # 同时匹配 python.model.yml 与 javascript.model.yml
```

而 `provider.rs::run_analysis` 是**按语言**分别调用 `--additional-packs <dir> --model-packs mcp-sec-audit-mad`。当分析 Python 数据库时，`javascript.model.yml`（`addsTo: codeql/javascript-all`）被一并加载，其 `sinkModel` 元组被解析到 Python 的 `sinkModel` 谓词上，造成列数不匹配 → 致命错误。

### 3.3 复现证据（对同一缓存 DB 实测）

| 实验 | 模型包内容 | 结果 |
|---|---|---|
| 原始（全量） | `python.model.yml` + `javascript.model.yml`，`dataExtensions: "*.model.yml"` | ❌ `Expected 4, but was 3`，exit 2 |
| 仅 python | 只放 `python.model.yml` | ✅ 通过，45 条标准查询全部跑完 |
| 作用域限定 | 两个文件都在，但 `dataExtensions: ["python.model.yml"]` | ✅ 通过 |

结论确定：**不是 3 列格式本身错（3 列是正确格式），而是「单 pack 塞两个语言、通配符全加载」导致跨语言污染。**

### 3.4 为什么之前的 G5「验证」没拦住

- MaD 注入被门控在 `CLI >= 2.26.3`（`mod.rs::mad_inject_supported`）。升级 CLI 之前（2.26.2）注入一直是**关闭**的，模型包根本没进到全量扫描里，bug 被隐藏。
- 历史跑批佐证：2.26.2 时代的多次运行 CodeQL 结果为 2 / 4 / 10（正常）；本次 2.26.3 后首次全量注入，立刻暴露为 0。
- 此前的「端到端验证」没有复现「多语言 model 文件 + 标准套件全量」这个组合条件，属于验证覆盖不足。

## 四、Taint 线噪声分析（P1）

212 条 Taint 结果，三大问题：

1. **sink 类型误判**：`openpyxl.load_workbook(filepath)` 是**文件读取**，却被标成 `network_request`。例如
   `taint:source:server.py:apply_formula:filepath:sink:inferred:call:server.py:107:20:network_request`
   （server.py:107 即 `load_workbook`）。这会让「网络请求」类漏洞被大量虚报，稀释真正危险的 sink。
2. **同构重复**：同一模式 `mcp_tool_parameter → file_read` 在 20+ 个工具函数里各报一条（`copy_range` / `delete_rows` / `merge_cells` / …），本质是同一条「filepath 参数流入文件读」的漏洞，未做聚合/去重。
3. **`file_read`/`file_write` 双向爆炸**：同一个 `filepath` 参数既报 `file_read` 又报 `file_write`，且 `sheet.py:271/306/424/439/452/467` 等位置反复出现，表明推断 sink 在跨函数传播时重复计数。

## 五、Agent 线表现（当前唯一亮点）

4 条结果全部命中真实问题，且都是 Taint/Rule 漏掉或降级的：

1. **get_excel_path 任意文件读写 + 路径穿越**（High）— 即 CVE-2026-40576 本体
2. **默认绑定 0.0.0.0 + 无鉴权**（High）— 暴露面问题
3. **公式注入：大小写敏感黑名单可绕过**（Medium）— `[A-Z]+\(` 只匹配大写，Excel 函数不区分大小写
4. **preview_only 参数被文档声明却未生效 → 全量数据外带**（High）

结论：B 线（agent）在**语义理解与跨函数因果推理**上明显强于 A 线（taint）与 C 线（codeql，当前瘫痪）。这正是差分框架要利用的信号，但前提是另两条线不能是「0 结果 + 纯噪声」。

## 八、改进方案

### 8.1 [P0] 修复 MaD 模型包：按语言隔离

`rust/crates/mcp-sec-audit-core/src/static_analysis/codeql/models.rs::write_model_pack_dir`

二选一（推荐方案 A）：

- **方案 A（按语言分包）**：为每个语言生成独立 pack（`mcp-sec-audit-mad-python` / `mcp-sec-audit-mad-javascript`），各自 `dataExtensions` 只指向本语言文件；`provider.rs::run_analysis` 按当前 DB 语言只传对应 pack。
- **方案 B（作用域限定）**：单 pack 保留，但 `dataExtensions` 从 `"*.model.yml"` 改为显式 `"<lang>.model.yml"`，并在 `MadPack` 上携带语言字段，按语言传入。

验证标准：对同一缓存 DB 重跑全量标准套件，`Expected 4, but was 3` 消失，CodeQL Results > 0。

### 8.2 [P0] 补 MaD 回归测试

新增集成测试（或 shell 级 gate）：构造同时含 python + javascript sink 的 catalog，断言生成的 pack 在做单语言 analyze 时**不触发** `Expected 4, but was 3`（最小化 DB，只跑 `UseofInput.ql` 或 `BindToAllInterfaces.ql` 即可触发）。同时把 `mad_inject_supported` 的门控与「实际能跑通」解耦——当前门控只判 CLI 版本，没判模型包可用性。

### 8.3 [P1] 修正 Taint sink 类型推断

定位 `facts/*` 与 `recon.rs` 中 sink kind 的推断逻辑：`openpyxl.load_workbook` 应归 `file_read` 而非 `network_request`。建议以**调用目标函数名/库名**而非「参数位置」决定 sink kind，并加入已知库→sink 映射表（load_workbook→file_read，requests.*→network_request，…）。

### 8.4 [P1] Taint 去重/聚合

按 `(source, sink_kind, sink_location)` 去重；同一 sink 点被同一 source 多次命中时只保留一条。目标：212 → 显著下降，且每条可读。

### 8.5 [P2] Fusion 聚合与置信度

- 对同一 sink 类别（如 `file_read`/`path_traversal`）跨函数的多条 finding 做**聚类**，合并为一条「filepath 参数通吃所有工具」的路径穿越结论，置信度按多线一致提升。
- 将 CVE 本体（agent 的 get_excel_path 结论）与 taint 的 `get_excel_path(...) → full_path` 数据流路径对价，`conf` 从 Medium 抬到 High。

### 8.6 [P2] 进化 promote 过滤 a2

核实 `pipeline.rs:504-522` 中 `delta` 是否包含 a2 误报；若包含，在 promote 前用 `migration.a2` 对应 key 过滤。同时考虑把「a2 规模」纳入 promote/rollback 决策（如 a2 占比过高时降级为「仅 promote 确认项」而非全量 delta）。

## 九、结论

本次运行暴露的**不是分析能力不足，而是工程接线问题**：MaD 机制上线即触发致命错误、C 线归零，A 线噪声未收敛，唯有 B 线稳定产出。修复 P0（MaD 按语言隔离 + 回归测试）后，三线才能在同一量级上进入差分对比，G1–G6 设计的「两阶段两线差分进化」闭环才算真正跑起来。
