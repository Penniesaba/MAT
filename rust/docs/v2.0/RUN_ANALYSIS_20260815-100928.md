## 一、目标 MCP 服务器的漏洞讲解（出题视角）

### 1.1 服务器概览

这是一个**故意植入漏洞**的最小 MCP（Model Context Protocol）服务器，用极简的 `MockMCP` 装饰器模拟 FastMCP 的 `@mcp.tool()` 模式，暴露三个工具：

| 工具 | 参数 | 漏洞 | 行号 |
|---|---|---|---|
| `run_shell` | `command` | 命令注入（Command Injection） | `server.py:72-87` |
| `read_log` | `filename` | 路径遍历 / 任意文件读取 | `server.py:90-102` |
| `fetch_url` | `url` | SSRF（服务端请求伪造） | `server.py:105-116` |

三个工具共同构成一个真实场景：一个「读日志 + 抓 URL + 顺便能跑 shell」的 MCP 服务，攻击面就是这三个入口。

---

### 1.2 漏洞 1：命令注入（`run_shell`）

**原理**：用户可控的 `command` 参数，经过一条跨函数调用链，最终进入 `subprocess.run(..., shell=True)`，由 shell 解释执行。

**调用链**：

```
run_shell(command)                 # server.py:73  入口（MCP tool 参数）
  └─ command_text = command.strip() # server.py:84
       └─ cmd_string = build_command(command_text)  # server.py:85 → 跨函数
            └─ f"sh -c '{cmd}'"     # server.py:55  拼接 shell 字符串，无转义
       └─ runner = sp.run          # server.py:83  赋值别名（import subprocess as sp）
            └─ runner(cmd_string, shell=True, ...)  # server.py:86  shell 执行
```

**利用方法**：`build_command` 用单引号包裹命令：`sh -c '{cmd}'`。攻击者只需在 `command` 里注入一个单引号即可闭合，例如：

```
command = "'; cat /etc/passwd; echo '"
```

拼出 `sh -c ''; cat /etc/passwd; echo ''`，达到**任意 OS 命令执行**。

**利用效果**：RCE（远程代码执行）。MCP 服务器通常以运行它的用户身份执行，等于拿到该主机完整控制权——读密钥、反弹 shell、横向移动。此外它本身就是把「裸 shell」作为一个一等工具暴露，见 1.5。

**考点**：`import subprocess as sp`（导入别名）+ `runner = sp.run`（赋值别名）+ 跨函数 `build_command`。规则线因为别名而**漏报**（正则只认 `subprocess.run`，不认 `sp.run`/`runner`），而 taint/CodeQL 因为做真实数据流而**能命中**。

---

### 1.3 漏洞 2：路径遍历 / 任意文件读取（`read_log`）

**原理**：用户可控的 `filename` 经过「伪归一化」函数 `normalize_path`（只 `strip()` 不做任何路径清理），拼接到固定目录上，再 `open()` 读取。

**调用链**：

```
read_log(filename)                 # server.py:91  入口
  └─ safe_path = normalize_path(filename)  # server.py:98 → 跨函数
       └─ return user_input.strip()        # server.py:47  无任何清理
  └─ full_path = Path("/var/log") / safe_path  # server.py:100
  └─ open(full_path, "r").read()           # server.py:101  任意文件读取
```

**利用方法**：`Path("/var/log") / safe_path` 有两条绕过路径：

1. **绝对路径覆盖**：`filename = "/etc/passwd"` → `Path("/var/log") / "/etc/passwd"` 结果就是 `/etc/passwd`（`pathlib` 的 `/` 遇到绝对路径会覆盖左侧）。
2. **`..` 上跳**：`filename = "../../../etc/shadow"` → 跳出 `/var/log` 目录。

**利用效果**：任意文件读取 → 机密性破坏。可读 `/etc/shadow`、`~/.ssh/id_rsa`、云凭证、服务源码等。配合 1.5 的「内容回传给模型」，读取结果还会被返回到模型上下文，进一步放大泄露。

**考点**：跨函数污点传播（`normalize_path` 被刻意做成「空校验器」），验证 taint 不会被一个徒有虚名的清理函数挡住。

---

### 1.4 漏洞 3：SSRF（`fetch_url`）

**原理**：用户可控的 `url` 经过一个**永远返回 True** 的「安全校验器」`is_safe_url`，直接传给 `requests.get()`。

**调用链**：

```
fetch_url(url)                     # server.py:106 入口
  └─ if not is_safe_url(url):      # server.py:113 伪校验
       └─ return True              # server.py:65  恒为 True，形同虚设
  └─ requests.get(url, timeout=5)  # server.py:115 直接外发
```

**利用方法**：因为校验恒真，任何 URL 都会被抓取，包括：

- 云元数据：`http://169.254.169.254/latest/meta-data/iam/security-credentials/`
- 内网服务：`http://localhost:6379/`、`http://internal-api/`
- 本地文件：`file:///etc/passwd`（部分 requests 版本支持）

**利用效果**：SSRF → 探测内网拓扑、读取云凭据、访问仅内网可达的服务，是云环境里最常见的高危入口之一。

**考点**：污点分析**不应**被「校验器函数」阻断——`is_safe_url` 恒真，taint 应穿透它直达 `requests.get`。

---

### 1.5 两个设计层面的问题（Agent 线发现，MCP 特有）

除了三个经典漏洞，Agent 线还额外报了 MCP 特有的两类问题：

1. **能力过度暴露（Capability over-exposure）**：把「任意 shell 执行」做成一个一等 MCP 工具，等于给任何能调用工具的模型直接发一把 root 权限的钥匙。对一个「读日志 + 抓 URL」定位的服务而言，这是不该出现的能力。
2. **上下文过度共享（Context over-sharing）**：工具把完整文件内容（`read_log`）和响应体（`fetch_url`）都返回给模型。若模型被 prompt injection 操纵，这些内部数据可被诱导外泄。

这两条不是「某一行代码写错」，而是**能力边界设计**问题，体现了 MCP 场景下「工具即攻击面」的特殊风险。

---

### 1.6 出题的「考点」设计总览

`server.py` 顶部的 docstring 自述了设计意图，逐一对应检测器的能力点：

| 设计特征 | 代码位置 | 考的是 |
|---|---|---|
| `import subprocess as sp` | server.py:19 | 导入别名解析 |
| `runner = sp.run` | server.py:83 | 赋值别名 / 变量跟踪 |
| `normalize_path` / `build_command` | server.py:40/50 | 跨函数污点传播 |
| `is_safe_url` 恒 True | server.py:58 | 穿透「伪校验器」 |
| `@mcp.tool()` 装饰器 | server.py:72/90/105 | 入口点检测 |

## 三、系统现状的问题、缺陷与改进方向

### 3.1 融合模块（最需要修）

**问题 1：标题 / 类别错配。**
报告第 1 条 `open(` 标题 + `network_request` 类别。根因在 `fusion/merger.rs`：`build_title` 优先取 `rule.matched_text`（`open(`），`build_category` 却做多类别投票（file_read 与 network_request 平票 → 取了 `network_request`）。两条仅隔一行的规则结果被 `matcher` 的「行临近 ≤5」强行并组，于是标题和类别来自不同结果。**建议**：组内标题与类别必须来自**同一条**主结果；规则结果的类别冲突应拆组或记 `conflict_notes`。

**问题 2：建议 / 路径错配。**
报告第 3 条：数据流路径指向 `read_log`（:101），建议却讲 `fetch_url` SSRF。`extract_recommendation` 取「组内第一个 agent 结果」的建议，`extract_paths` 却取「组内 codeql 结果」的路径，二者没有对齐到同一条子结果。**建议**：路径、建议、标题、类别应绑定到同一个「主结果」上整体提取，而不是各自独立取「第一个」。

**问题 3：多线印证反而丢了路径。**
报告第 2 条（taint+agent+codeql 三条线印证）反而**没有** Dataflow path。根因在 `merger.rs:extract_paths`：只要组内有 taint 就 `return taint.dataflow_path`，**永远不走** codeql 那条更完整的路径链。taint 的直接 source→sink 单跳没有中间步 → 空路径，于是把 CodeQL 已经算好的 `73→84→…→86` 丢弃了。**建议**：`extract_paths` 应优先取**非空**的路径，或 codeql 路径优先于 taint 空路径。

**问题 4：丢结果。**
Agent 的「Context over-sharing (Medium)」在融合后消失。需要排查是 matcher 把它并进了别的组（标题被覆盖）还是 scorer 过滤掉了。**建议**：为每条原始结果记录「是否进入某个 fused finding」，缺失时输出告警。

**问题 5：`require_confirmed_by = 1` 名不副实。**
配置是「≥1 条线就保留」，等于任何单线独报都算数。报告 6 条里 5 条是单线/错配，所谓「融合」更像「汇总 + 贴标签」。**建议**：默认提为 2，让「多线印证」真正生效。

### 3.2 各线路的盲区

| 线路 | 盲区 | 证据 |
|---|---|---|
| **rule** | 纯文本匹配，不分注释/字符串/docstring，且被别名绕过 | 命中 `server.py:8/9`（docstring），漏掉 `sp.run`/`runner` 的命令注入 |
| **taint** | sink 覆盖不全 | 没有 `open`/文件读取 sink → 漏 read_log |
| **codeql** | SSRF 查询的 source 限定太窄 | `ResourceToNetwork.ql` 只认 `@mcp.resource()`，不认 `@mcp.tool()`；`ToolParameterToSink` 的 sink 不含 `requests.*` → 漏 fetch_url |
| **agent** | 非确定性 | 5 条结果每次运行不同（LLM 天然不稳） |

**改进方向**：
- rule：跳过 docstring/注释/字符串字面量；对别名做「导入别名 → 真实名」归一化后再匹配。
- taint：补齐 sink 目录（`file_read`、`file_write`、`sql` 等），与 rule/agent 的 sink 分类对齐。
- codeql：给 SSRF 单独一个 `@mcp.tool()` 为 source、`requests/httpx/urllib/socket` 为 sink 的查询；把 `requests.get` 等网络 sink 纳入 `ToolParameterToSink`。
- agent：固定 model + 低温度，或多次运行取交集，提升可复现性。

### 3.3 报告渲染问题

1. **建议被硬截断**：`extract_recommendation` 把 agent 的 `reasoning_summary` 截到 200 字符加 `…`，报告里建议常在半句话断掉（如第 2、3 条）。**建议**：markdown 里输出完整建议，或把 200 截断只用于摘要、完整版放 JSON。
2. **类别为 `unknown`**：agent 单飞的发现（第 5、6 条）类别是 `unknown`，虽标题能说明问题，但不利于分类统计。**建议**：让 agent 结果也带一个类别，或在融合时从标题/关键词推断。
3. **路径展示不一致**：有的发现显示 `Dataflow path`，有的不显示（见 §3.1 问题 3），读者无法判断「无路径」是「真无」还是「被丢了」。

### 3.4 其它架构问题

1. **严重度与置信度混为一谈**：taint/agent 结果结构里没有独立 severity 字段，fusion 用 confidence 硬映射 severity（`scorer.rs`）。「有多确定」和「有多严重」是正交的两个维度，被合并会误导排序。
2. **四条线四种数据结构**：`Rule/Taint/Agent/CodeqlAnalysisResult` 各不相同，fusion 得写大量适配代码去对齐，这也是「关联不起来」的结构性原因。可考虑抽象一个统一的中间结果结构。
3. **故障静默降级**：任一线路失败，用户看到的是「少了几条」而不是「这条线挂了」。应把每线失败/超时/空结果显式写进报告。

### 3.5 改进优先级建议

1. **修 `extract_paths` 的 taint 优先导致丢路径**（影响最直接、改动最小）。
2. **修融合的属性错配**（标题/类别/建议/路径绑定到同一条主结果）。
3. **补 codeql 的 SSRF 查询**（当前三个漏洞里 SSRF 是 CodeQL 的覆盖空洞）。
4. **rule 线跳过 docstring/注释**（消除 `server.py:8/9` 这类「定位到文档」的噪声）。
5. **默认 `require_confirmed_by = 2`**，让「多线印证」名副其实。
6. **报告输出完整建议 + 每线诊断告警**。

## 附：一句话结论

这次运行在**漏洞发现层面是成功的**——四线并集覆盖了全部三个经典漏洞（命令注入、路径遍历、SSRF）外加两个 MCP 设计问题，且 CodeQL 给出了漂亮的数据流路径链。**短板在「融合」**：结果能汇总，但标题/类别/建议/路径互相错配、多线印证时反而丢路径、还丢了一条 agent 结果。下一阶段的重点应是「让融合真正对齐」，而不是继续堆检测器。
